# Multiplayer

Enable **Multiplayer** in the launcher or **Project settings**. Starter projects create a separate character for each player; existing single-player scripts need to be split into server logic and client presentation. Multiplayer supports both 2D and 3D scenes.

## Test in Studio

Press **Play**. Studio opens a dedicated host and one client. **Add client** creates another independent game runtime (up to eight in Studio). Each client has its own Lua VM, modules, UI, camera, input focus and WebSocket connection. Click a canvas to control that client; blur releases its keys. **Disconnect** removes a client; **Stop server** closes the entire session. The server panel shows connected players, simulation time and recent server logs. Edits are isolated from all runtime copies.

Use packaged desktop Studio, or `npm run dev` on localhost. A static Studio website cannot start a native server process. Development host-control endpoints accept loopback requests only and reject foreign browser origins. Studio binds game servers to localhost on an automatically allocated port; exported servers bind to all interfaces by default.

## Scripts and shared data

| Class                   | Single player       | Multiplayer server          | Multiplayer client                       |
| ----------------------- | ------------------- | --------------------------- | ---------------------------------------- |
| `Script`                | Runs                | Runs (legacy server script) | Excluded                                 |
| `ServerScript`          | Runs                | Runs                        | Excluded                                 |
| `LocalScript`           | Inactive            | Inactive                    | Runs                                     |
| `ModuleScript`          | Loaded by `require` | Loaded by `require`         | Loaded by `require`                      |
| `PlayerController2D/3D` | Runs                | Inactive                    | Runs only for its directly owning player |

LocalScripts inside a leased physical object run only on its current owner; shared LocalScripts outside leased objects run on every client. Modules have a separate cache on each side. Put shared modules/templates in ScriptService or another replicated folder. Put **private modules under a ServerScript**: entire ServerScript and legacy Script subtrees are omitted from client documents, network snapshots and exported client project files. Assets and replicated modules are public to clients. The web server serves only its client HTML and `/health`; it does not serve `project.json` or server source.

`RunService:IsServer()` and `RunService:IsClient()` identify the active side. Both return true in standalone games, where there is no network boundary. `typeof(value)` identifies `Vector2`, `Vector3` and `Instance` values received by Lua.

## Players

```lua
local players = game:GetService("Players")
players.PlayerAdded:Connect(function(player)
    print("Joined", player.Name, player.UserId)
end)
players.PlayerRemoving:Connect(function(player)
    if player.Character then player.Character:Destroy() end
end)
```

`OnPlayerAdded` / `OnPlayerRemoving` are aliases. `GetPlayers()` returns a snapshot; `GetPlayerByUserId(id)` and `GetPlayerFromCharacter(character)` perform lookups. On clients, `Players.LocalPlayer` is assigned before LocalScripts start. Read `LocalPlayer.Character`, or subscribe to its `CharacterAdded` signal. The server calls `player:SetCharacter(instance)` to publish a character or respawn. Scripts can enumerate already joined players as well as subscribing to future joins.

`UserId` is a random UUID generated by the host for that connection. It is **a session identity**, not an account ID or authentication credential. Reconnecting creates another ID. Player names are short display strings and need not be unique. Never use a client-provided name as an authorization decision.

## RemoteEvents

Insert a RemoteEvent into Workspace or a shared folder and give it a name. Clients send intentions; servers validate and decide results.

```lua
-- LocalScript
local request = workspace.Purchase
request:FireServer("Medkit", 1)
request.OnClientEvent:Connect(function(success, message)
    print(message)
end)
```

```lua
-- ServerScript
local request = workspace.Purchase
request.OnServerEvent:Connect(function(player, item, quantity)
    -- The first argument comes from the connection, never from client payload data.
    if item ~= "Medkit" or quantity ~= 1 then return end
    -- Check balance, cooldown and inventory here, then apply the purchase.
    request:FireClient(player, true, "Purchased")
end)
-- request:FireAllClients("Announcement") broadcasts to every connected client.
```

Arguments support nil, booleans, finite numbers, strings, arrays, data tables, Vector2/Vector3 values and references to replicated instances. Unsupported executable values, cycles, reserved protocol keys and excessive depth are rejected. Unknown instance references resolve to nil. Pass player IDs as strings when identifying players in a payload. RemoteEvents accept at most 32 positional arguments. Client-to-server packets are limited to 16 KiB, nesting to 12 levels, and a connection has a shared 120-packet/second token budget (including physics). Scripts must still validate action types, ranges, permissions, cooldowns and game rules. `FireClient` and `FireAllClients` are server-only; `FireServer` is client-only. Remotes are transient messages; use replicated attributes for durable state and late joins.

## Physics ownership and replication

```lua
-- ServerScript: publish an unanchored character, then lease its physics to its player.
local actor = script.Parent.Templates.Player:Clone()
actor.Parent = workspace
actor:SetNetworkOwner(player)
player:SetCharacter(actor)
-- actor:SetNetworkOwner(nil) gives control back to the server.
-- actor:GetNetworkOwner() returns the owning Player or nil.
```

Ownership applies to **one physical object**, not its descendants. A PlayerController directly inside that object starts on its owning client and stops when ownership is revoked. Other clients receive static physical replicas; their renders interpolate remote transforms over 50 ms. The host keeps simulating all bodies, accepts only the assigned owner's position/velocity/rotation updates and distributes authoritative results. Server-assigned `Position` changes carry a correction generation so server teleports and respawns override the owner's prediction; stale samples cannot undo a teleport. Disconnecting revokes remaining leases. The project decides whether to destroy or preserve abandoned objects.

The fixed simulation runs at 60 Hz. Scene changes and owned-body samples are sent at 20 Hz; late joins receive the current full scene, then only changed/deleted instances. Names, attributes, object properties, hierarchy changes, new objects, deletions, controllers, script enablement, gravity and character references replicate from the server. UI, audio, input, cameras and arbitrary Lua module state do not replicate. Client-created cosmetic objects remain local and survive snapshots; deleting their server parent also deletes those children. Client edits to replicated properties/attributes can be overwritten by subsequent server changes. Persist gameplay state as serializable data attributes on the server. Server runtime-only function/instance attributes cannot be serialized into network scenes; keep such data in Lua tables/modules instead.

The host rejects unowned/anchored updates, nonfinite transforms, stale correction generations and excessive position/velocity changes. Current ceilings are 80 m/s in 3D, 4,000 px/s in 2D, bounded per-sample displacement, and 100,000 world units from origin. These are coarse abuse guards, **not competitive anti-cheat**: a leased client still influences its object's movement within the bounds. Keep sensitive physics and combat on the host. This initial protocol has no lag-compensated hit rewind, rollback, streaming interest management, matchmaking, persistent accounts, encryption without TLS, automatic reconnect or cross-version negotiation. Host and clients must use the same engine release. The host caps connections at 32; this is a hard cap, not a verified capacity claim. Large worlds need profiling and replication budgeting before production deployment.

## Web deployment

Build **Web game ZIP** in Studio, or:

```sh
npm run package:game -- --project examples/neon-borough/project.openengine --platform web
```

Extract the ZIP on a computer with **Node.js 24 LTS** and run:

```sh
node server.cjs
```

No `npm install` is required in the export. Open `http://localhost:7777` on the host, or `http://SERVER-IP:7777` from another computer. The page preselects the matching WebSocket address; enter a display name and click **Join server**. Separately distributed client HTML defaults to localhost and lets players enter `ws://SERVER-IP:7777/socket`. A `?server=wss://example.com/socket` URL parameter can select a hosted server.

`HOST` defaults to `0.0.0.0`; `PORT` defaults to `7777`. Allow that TCP port through the host firewall. For public hosting, place it behind an HTTPS reverse proxy that forwards WebSocket upgrades to `/socket`, and use `wss://` clients. HTTPS pages cannot connect to insecure `ws://` hosts. Run under a process supervisor and set deployment-specific access/resource limits. A normal static website alone cannot run authoritative Lua/physics; the Node host must stay running. Ctrl+C stops the command-line host.

Only distribute `index.html` to players if hosting separately. Keep `project.json` and the server runtime on the host. Third-party notices ship in both the runtime and export.

## Windows deployment

Packaged desktop Studio's **Desktop game** export creates two sibling distributions: the game client and a **Server** application. Keep each entire application folder intact. Start the Server executable, then run the client executable on each player's computer. The server window shows its listening port, connected players and logs, with a **Stop server and exit** button. Clients choose their name and WebSocket address. The default is `ws://localhost:7777/socket`; replace localhost with the host's LAN/public address on other computers. No Node.js install is required for the native server.

From source:

```sh
npm run package:game -- --project examples/neon-borough/project.openengine --platform win32
```

The CLI produces `NeonBorough-win32-x64/NeonBorough.exe` and `NeonBoroughServer-win32-x64/NeonBoroughServer.exe`. Send the **client folder** to players. The server folder contains private game code. Native server and client use the same wire protocol as web builds, so web and native players can share a host. The native Server application requires a desktop session; use the Node export for headless/cloud hosting. `PORT` and `HOST` environment variables also configure the native server.

## Neon Borough

This original, primitive-art online city sandbox demonstrates eight walking residents, three enterable arcade coupes, shared combat and respawning. It uses no franchise assets or external artwork.

- WASD walks; Space jumps; hold right mouse and drag to look.
- Left mouse fires along the center crosshair. The host raycasts, limits the firing rate and applies 25 damage. Four hits cause a takedown; players respawn after four seconds and residents after eight. Resident takedowns award 10 swag, player takedowns 50; swag and takedown counts survive respawns in the same connection. Overhead labels show every player’s replicated swag, and high-speed vehicle impacts can also earn it.
- Walk beside a car and press E to enter. WASD drives/steers; E exits. Cars are server-controlled, and stale input brakes them after half a second.
- Player names, online count, HP and takedowns appear in each client's own UI. Resident movement, tracers, vehicle movement and game-state attributes replicate to all players.

Cars accelerate/brake gradually and climb the lowered curbs. Default controllers step onto low edges and follow walkable ramps. Vehicles and residents use the same movement helper; lost/destroyed residents recover. `NeonBorough-source.zip` contains a dedicated portable project plus editable Lua/scene source.

`examples/neon-borough/scripts/Config.lua` holds shared tuning. `Server.lua` owns the rules and `Client.lua` handles presentation/input. `tools/create-city.mjs` regenerates the editable city scene. It is a compact demonstration, not a full open-world commercial game: vehicles use an arcade body rather than wheel suspension; characters/residents use simple colliders rather than skeletal animation.
